# Models and prompts

## Choosing a model

Every worker is a Droid session: the office runs one detached [Droid CLI](https://docs.factory.ai/cli/getting-started/quickstart) daemon (`droid daemon`, resolved from `--agent`, default `droid`; `DROID_OFFICE_AGENT` changes it) and manages each local worker and the Orchestrator as a JSON-RPC session (`initializeSession`, or `loadSession` to resume or reattach a saved session).

The hire, hand-off and Subagents windows list every model droid can run, the same list as droid's own model picker: the office asks `droid daemon` for it (`droid.list_models`, falling back to `droid exec` or the models your own `~/.factory/settings.json` names — every custom model, plus your session default and favorites — when the daemon can't answer) and caches it for a minute. Each model field is a searchable picker rather than the system dropdown: type to filter by name, id or provider, use the chips to show only your own models or one provider, and read the credit multiplier on every row. The last four picks sit on top as **Recent**. Your own models are grouped by the gateway that serves them (DroidProxy, OpenRouter…), Factory's by provider, with legacy ones last; disabled models are left out, and the effort list (low, medium, high, xhigh or max) offers only the efforts the picked model takes, its own default named on **Default**. Leave the model on **Default** to run the office's Default worker (below), or whatever your Droid settings say when none is set; the option names the model and effort it runs, such as **Default (Opus 5.5)**. A pick is pinned for that worker only: the office passes `modelId` and `reasoningEffort` straight to `initializeSession` / `loadSession`, keeping the choice with the worker across resumes without touching `~/.factory/settings.json`.

Set the office's **Default worker** in ⚙️ Settings → **Models**: a model and effort for workers with no explicit choice. Until you set it, they start on `--agent` with Droid's own default model, as they always have. The hire and ask windows keep their own pickers and memory; a choice made there wins over the default.

Every local Droid session starts and resumes on `droid daemon` with auto-approved tool execution (`skipPermissionsUnsafe: true`, `interactionMode: 'auto'`, `autonomyLevel: 'high'`, `disableInactivityTimeout: true`, plus `daemon.request_permission` answered `'proceed_once'`), per-session inline HTTP `mcpServers` (`droid-office`, omitting `oauth`) pointing at a token-protected loopback endpoint, and `disabledToolIds: ['Task']` unless **Settings → Subagents & visits → Droid’s Task tool** allows it — all without editing `~/.factory/settings.json` or `~/.factory/mcp.json` (any legacy `droid-office` entry in `~/.factory/mcp.json` is cleaned up once at startup). Daemon `session_notification` events drive worker status, live Thread activity and structured `AskUser` questions directly, while mid-turn office notices (a visit, its lead's message, a Whiteboard button) steer or queue through `add_user_message` (`EndOfTurn` vs `EndOfLoop`). Every Droid worker also starts, and resumes, with the **Worker system prompt** appended to Droid's preset system prompt (`systemPrompt: { type: 'preset', preset: 'droid', append }`). It tells the worker it's in Droid Office and what the office gives it (Droid already tells every session its folder, branch and git status): subagents are hired with `team_hire` rather than Droid's Task tool, and anything you should look at (screenshots, mockups, plans, choices) goes on the Whiteboard with Office MCP Whiteboard tools. A worker you hired yourself (not a subagent) is also told about the Office MCP visit tools, for visiting the other workers on its floor, while visits are on. The **Office MCP** switch in Settings controls these tools; see [Office MCP](../office-mcp.md). Rewrite or empty the prompt under **Every worker** in the prompt editor. Changing a worker's model or effort in its Thread header (or through `worker_model`) updates the running session live via `daemon.update_session_settings`, and `session_settings_updated` notifications keep the badge next to the worker matched to what it really runs.

## Subscriptions

On a Mac with Apple silicon, workers can run on the Claude or ChatGPT plan you already pay for, and on Grok, Meta, GitHub Copilot and the other providers [DroidProxy](https://github.com/nikships/droidproxy) serves. DroidProxy is a small menu-bar app that signs in to those plans and hands their models to Droid as your own custom models. You don't need to set it up yourself: ⚙️ Settings → **Connections** (and the welcome's Subscriptions step) does it.

- **Connect** a provider, and the office installs DroidProxy from its GitHub releases if it isn't there (it checks the SHA-256, that it's signed by DroidProxy's developer and notarized by Apple), starts it in the background, and opens the provider's sign-in in your browser or shows a device code. When the first account of a provider is connected, the office puts DroidProxy's models into Droid's settings (`~/.factory/settings.json`, with a backup) and they show up in every model picker under **DroidProxy**. **Update models** puts them back after a provider changed. **Add another** connects a second account of the same provider, which DroidProxy uses when the first runs out.
- Each account shows how much of each usage window (5-hour, weekly…) is left and when it resets. The pane also shows DroidProxy's version, offers **Update** when a newer one is out (that quits and restarts DroidProxy), and **Open DroidProxy** for its own settings window, where everything else lives.
- An older DroidProxy without the control API the office drives it through is shown as needing an update, and its accounts are read from its usage page.
- Off a Mac with Apple silicon, the pane says Subscriptions need DroidProxy on a Mac.

### Models that can't run

Every model you enabled stays yours to pick, by you and by leads hiring subagents. The office only refuses a model a worker couldn't run on: its provider has no signed-in account, the provider is switched off in DroidProxy, every account is out of quota (with when the first one comes back), or DroidProxy isn't installed. The pickers show such a model dimmed with the reason and won't pick it, a hire on one is refused with the same words, and `team_models` marks it, so a lead picks another. For a model that can run, `team_models` also shows what its plan has left (each window's percent left and when it resets), so a lead can favor a plan with plenty of quota. When nobody can tell (an older DroidProxy, a provider without a usage reader, DroidProxy not answering for a few minutes), nothing is refused. A hire on a DroidProxy model while DroidProxy is installed but stopped starts it and goes ahead.

## The office's prompts

Everything the office tells a worker by itself can be rewritten in ⚙️ Settings → **Workers** → **Prompts**: the system prompt every Droid worker starts with (empty adds none; a change reaches a worker the next time its session starts or resumes), what **Hand to a worker**, **Review**, **Fix up & merge**, **Fix conflicts & merge** and **Ask a worker…** send from the issue and pull request boards, what **Commit & open PR** asks a worker from its Changes window, the brief written into a workspace when one task spans several repositories, the task **Have a worker set it up…** writes for a repository's worktree setup, the line **Ping a worker** sends a worker from the Whiteboard, the reminders a lead and its subagents get as a turn ends, and the instructions for the model that writes the signs over workers' heads. Each one lists its `{{placeholders}}` (the issue number, the PR's branch, and so on), which the office fills in when it sends it, and warns when one the office counts on is missing. On a GitLab floor the same prompt reads in GitLab's words: `{{site}}`, `{{cli}}`, `{{pullName}}`, `{{ref}}`, `{{read}}`, `{{checkout}}`, `{{merge}}` and the rest become GitLab, `glab`, merge request, `!12` and the `glab mr` commands, so the office's own wording is word for word what it sends on each forge. **Default** puts the office's own wording back. The Linear ticket hand-off and autopilot prompt is editable as **Linear ticket**; the Jira board's hand-off prompt is not. They're the same on every floor and kept in the office's `.droid-office/prompts.json`, with the Default worker.
